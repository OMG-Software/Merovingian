# Release process

This document describes the current release path for The Merovingian.

## Alpha prereleases

Alpha packages are published from Git tags that match this pattern:

```text
v*-alpha*
```

Pushing a matching tag triggers [release.yml](../.github/workflows/release.yml).
That workflow:

- builds hardened packages for Linux and FreeBSD (`linux-alpha-package`,
  `freebsd-alpha-package`) — OpenBSD and NetBSD packages are not part of the
  alpha release workflow; they are built by the rolling `packages.yml`
  workflow and published to its `latest` GitHub release instead
- runs the full Meson test suite on both platforms
- runs Linux phase 1 configuration validation
- runs the unsafe-source gate
- runs release-readiness metadata checks
- packages `merovingian-server` and `merovingian-db-migrate`
- attaches SHA-256 checksum files
- collects release evidence per platform (`scripts/collect-release-evidence.sh`):
  compiler version, link-time hardening confirmation
  (`scripts/check-elf-hardening.sh`), pinned dependency versions from
  `subprojects/*.wrap`, the test log's Ok/Fail/Timeout summary, and the
  mandatory fuzz target list — folded into the published release notes
  alongside the package checksums
- publishes a GitHub prerelease with the built assets

Each tarball carries a SLSA provenance attestation generated by
`actions/attest-build-provenance` and verifiable with:

```sh
gh attestation verify <tarball> --repo OMG-Software/Merovingian
```

Published releases also trigger [sbom.yml](../.github/workflows/sbom.yml),
which generates SPDX and CycloneDX JSON SBOM files and attaches them to the
GitHub release as `merovingian.spdx.json` and `merovingian.cdx.json`.
Repository changes are additionally covered by:

- [secret-scan.yml](../.github/workflows/secret-scan.yml) for Gitleaks-based
  history scanning
- [dependency-vulnerability-triage.yml](../.github/workflows/dependency-vulnerability-triage.yml)
  for PR dependency review and SBOM-backed vulnerability triage
- [pages.yml](../.github/workflows/pages.yml), which builds the documentation
  site with `mkdocs build --strict` on every branch and pull request and
  deploys it to <https://omg-software.github.io/Merovingian/> from `main`, so
  the published documentation always matches the latest merged release line

The packaged tarballs include:

- `bin/merovingian-server`
- `bin/merovingian-db-migrate`
- `config/merovingian.conf.example`
- `docs/user-manual.md`
- `docs/release-process.md`
- `docs/security-review-checklist.md`
- Linux and BSD packaging scaffolds, including Debian control metadata, RPM
  spec metadata, FreeBSD manifest metadata, OpenBSD packing-list metadata, and
  NetBSD/pkgsrc Makefile metadata
- `README.md`
- `LICENSE`

## Starting a minor series: the upgrade fixture

Upgrades are supported from 1.0.0 onward, so this applies to minor series from 1.1 on.
A database written by the previous supported minor series must open, migrate and serve
under every candidate (ADR-0216). When the first version of such a series is cut (for
example 1.1.0), add the fixture of the last release of the series before it (there,
the last 1.0.x release):

```bash
python scripts/generate_upgrade_fixture.py <last-release-commit> tests/fixtures/upgrade/<last-release-version>
```

Then add scenarios to `tests/integration/test_database_upgrade_flow.cpp` that open that
fixture and serve it, and remove the previous fixture directory. Never regenerate a fixture from current code: it is
evidence only because the old release wrote it.

A pre-1.0 series start (such as 0.13.0) adds no fixture and no upgrade test. The
migrations were collapsed into one initial schema in 0.12.47
([ADR-0224](adr/0224-pre-1-0-migrations-collapse-into-one-frozen-v1-schema.md)), so a
pre-1.0 database can no longer be opened: that change removed the 0.11.13 fixture and
its scenarios, and there is no fixture until the 1.1 series starts.

### The v1 schema is frozen from 1.0.0

From 1.0.0, the v1 migration (the `initial_schema` step in `src/database/migration.cpp`)
and `migrations/001_initial_schema.sql` never change. A schema change is a new numbered
migration (v2 onwards) that keeps deployed databases compatible. A unit test requires the
SQL file to match the build's v1 step statement for statement.

## Verifying release signatures

Every release tarball and package is accompanied by a detached GPG signature
(`.asc`). The signing key is an offline, long-lived maintainer key stored as a
GitHub Actions secret. Operators can verify artifacts without the GitHub CLI.

```sh
gpg --keyserver keys.openpgp.org --recv-keys 66DFCC50187C8E46B5ED85FD92A3A264F0A7BE20
```

Verify a release artifact:

```sh
gpg --verify merovingian-<version>-linux-x86_64.tar.gz.asc \
  merovingian-<version>-linux-x86_64.tar.gz
```

If the signature is valid, GPG reports a good signature from the maintainer
identity. A missing or invalid signature must be treated as a build or
distribution failure.

Release assets also include:

- `SHA256SUMS` for every package (in rolling `latest` releases)
- per-tarball `.sha256` files for alpha releases
- `merovingian.spdx.json` and `merovingian.cdx.json` SBOMs
- `merovingian.licenses.json` machine-readable license summary

## Operator sequence

The release operator should still run the normal local evidence path before
creating the tag:

```sh
sh scripts/setup-dev-env.sh --check-only
meson setup build -Dbuild_tests=true -Dbuild_fuzz=true
meson compile -C build
meson test -C build --print-errorlogs
sh scripts/reject-unsafe.sh
sh scripts/check-release-readiness.sh
```

Then run Complement against the candidate (see "Complement" below). It must be green
before the tag is created.

After that, create and push an alpha tag:

```sh
git tag v<version>-alpha.1
git push origin v<version>-alpha.1
```

GitHub Actions publishes the prerelease assets for that tag.
The matching release event also publishes the SBOM assets, and the scheduled
dependency-triage workflow keeps a separate vulnerability report artifact.

## Complement

The external Complement suite runs against the candidate's Debian trixie package before
the tag, and its signed result is attached to the release afterwards (ADR-0233, ADR-0234,
ADR-0235). Prerequisites are in `docs/dev-environment.md`, "Complement".

1. Take the candidate from the rolling `latest` prerelease built from the release
   commit: the Debian trixie package and its signature, and the checksums and theirs:

   ```sh
   gh release download latest --repo OMG-Software/Merovingian --dir candidate \
     --pattern 'merovingian_*_amd64-debian.deb*' --pattern SHA256SUMS --pattern SHA256SUMS.asc
   ```

2. Run Complement. The work directory must be empty, and the exit status is the verdict.
   Besides the signed checksums, the run checks the package's build provenance with
   `gh attestation verify`. `packages.yml` must have built exactly this file from one
   commit on `main`, and the run records that commit:

   ```sh
   python3 scripts/run_complement.py \
     --package candidate/merovingian_<version>_amd64-debian.deb \
     --sha256sums candidate/SHA256SUMS --signature candidate/SHA256SUMS.asc \
     --work-dir ../complement-<version>
   ```

   A failure outside `tests/complement/skip-list.toml` is fixed, or listed with the
   evidence its category needs (`tests/complement/AGENTS.md`). A stale or missing
   entry is removed. Either way the run is repeated from an empty work directory.

3. Record the evidence. The exit status is 0 only for release evidence:

   ```sh
   python3 scripts/record_complement_evidence.py --work-dir ../complement-<version> \
     --package candidate/merovingian_<version>_amd64-debian.deb --output-dir ../complement-evidence
   ```

4. Tag the commit the run recorded (`source.commit` in the results), and push the tag
   (above). Once the release workflow has published the release, sign and attach the
   evidence and the tested package. The publisher refuses a tag at any other commit:

   ```sh
   python3 scripts/publish_complement_evidence.py \
     --results ../complement-evidence/complement-results-<version>.json \
     --log ../complement-evidence/complement-<version>.jsonl \
     --package candidate/merovingian_<version>_amd64-debian.deb \
     --package-signature candidate/merovingian_<version>_amd64-debian.deb.asc \
     --tag v<version>-alpha.<n>
   ```

The release notes' Complement section names the files. Readers verify each like any
other asset (`gpg --verify <file>.asc <file>`). The tested package's SHA-256 must equal
the `package.sha256` the results record, and its `/usr/bin/merovingian-server` the
`server_sha256`.

## Rolling latest packages

Pushes to `main` also trigger [packages.yml](../.github/workflows/packages.yml).
That workflow rebuilds packages for all supported platforms, replaces the
rolling `latest` GitHub prerelease, and uploads fresh package checksums:

| Artifact | Job |
|---|---|
| Ubuntu `.deb` | `deb` |
| Debian trixie `.deb` | `debian-pkg` |
| Fedora `.rpm` | `rpm` |
| RHEL-compatible `.rpm` (AlmaLinux 10) | `rhel-rpm` |
| OpenSUSE Tumbleweed `.rpm` | `opensuse-rpm` |
| FreeBSD `.pkg` | `freebsd-pkg` |
| OpenBSD `.tgz` | `openbsd-pkg` |
| NetBSD `.tgz` | `netbsd-pkg` (retried once on QEMU infrastructure failure) |
| Portable static Linux tarball (musl) | `static-linux-fallback` |

Every packaging script configures Meson with `--buildtype=release`. Meson's
default `debug` build has no `_FORTIFY_SOURCE`, and the server refuses to start
when its startup hardening self-check cannot confirm it
([ADR-0148](adr/0148-packaging-paths-pass-buildtype-release-explicitly.md)).
A new packaging path must do the same, and be added to `PACKAGING_SCRIPTS` in
`tests/tooling/test_packages_workflow.py`.

Before attesting, the `deb` and `debian-pkg` jobs install the package they
built and run `scripts/check-startup-hardening-gate.sh` against the installed
`/usr/bin/merovingian-server`, as the `merovingian` user with an empty
capability bounding set. The job fails unless every startup hardening check
reports `enabled` and the server stops cleanly. The `docker-image` job does the
same for the `Dockerfile`: it builds the image and runs the gate inside it with
`--cap-drop=ALL --security-opt=no-new-privileges`. The image is not published;
the job is a gate on the recipe.

The `Dockerfile` pins `debian:trixie-slim` by the digest of its
multi-architecture index. To move to a newer base, read the current digest
(for example `docker buildx imagetools inspect debian:trixie-slim`, the
`Digest:` line of the index, not a per-platform manifest), replace it in both
`FROM` lines, and let the `docker-image` job prove the new image still passes
the gate.

Each package is individually attested with
`actions/attest-build-provenance` before upload, verifiable with:

```sh
gh attestation verify <package-file> --repo OMG-Software/Merovingian
```

The publish step also creates a detached GPG `.asc` signature for every
package (including `SHA256SUMS`) using the maintainer key. Verify with:

```sh
gpg --verify <package-file>.asc <package-file>
```

The publish step resolves and deletes the existing `latest` release with an
explicit `--repo "${{ github.repository }}"` scope before recreating it so the
artifact-only job does not depend on checkout state.

The static Linux fallback artifact is built on Alpine/musl with `-static-pie`
and packaged as `merovingian-<version>-linux-static-x86_64.tar.gz`. It is a
portability fallback for older Linux distributions that cannot easily consume
the `.deb` or `.rpm`; distro packages remain preferred where available because
their OpenSSL, libsodium, and libpq dependencies receive normal OS security
updates.
