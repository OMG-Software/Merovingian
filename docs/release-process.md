# Release process

This document describes the current release path for The Merovingian.

## Tagged releases

A release is published from a Git tag that names the version in `meson.build`:

```text
v<version>
```

Pushing any `v*` tag triggers [release.yml](../.github/workflows/release.yml)
(ADR-0597). That workflow:

- refuses the tag, before anything is built, unless it is exactly
  `v<meson.build version>` (`check-tag`); a suffixed tag such as
  `v0.12.90-alpha.1` is refused
- builds every package the rolling `latest` release carries, by calling
  `packages.yml` (`distro-packages`): the same jobs build, attest, stage and
  sign them for the tag as for `main`, and install and boot the Ubuntu, Debian,
  Fedora and FreeBSD packages through the startup hardening gate, so a tag ships exactly
  the `latest` set, every package x86_64, hardened-profile and named after the
  platform it installs on (see "Rolling latest packages" below,
  [ADR-0742](adr/0742-build-test-and-package-platform-lists-and-a-tag-ships-what-latest-ships.md))
- builds and tests Linux and FreeBSD 15 with the hardened profile
  (`linux-release-evidence`, `freebsd-release-evidence`) as release gates and
  for the release evidence; neither build is published
- runs the full Meson test suite on both platforms
- runs Linux phase 1 configuration validation
- runs the unsafe-source gate
- runs release-readiness metadata checks
- publishes `SHA256SUMS` over every asset
- generates the SBOM (`scripts/generate_sbom.py`, ADR-0598) and the licence
  summary before signing, so both carry detached GPG signatures
- collects release evidence per platform (`scripts/collect-release-evidence.sh`):
  compiler version, link-time hardening confirmation
  (`scripts/check-elf-hardening.sh`), pinned dependency versions from
  `subprojects/*.wrap`, the test log's Ok/Fail/Timeout summary, and the
  mandatory fuzz target list — folded into the published release notes
  alongside the package checksums
- publishes a GitHub release with the built assets, marked as a prerelease
  for every `0.x` version and as a full release from 1.0.0

Each published package, the static tarball among them, carries a SLSA
provenance attestation generated by `actions/attest-build-provenance` in
`packages.yml`, which the tag's `release.yml` run calls, and is verifiable with:

```sh
gh attestation verify <package-file> --repo OMG-Software/Merovingian \
  --signer-workflow OMG-Software/Merovingian/.github/workflows/packages.yml \
  --source-ref refs/tags/v<version>
```

Keep both `--signer-workflow` and `--source-ref`. With `--repo` alone the check
accepts an attestation from any workflow on any branch of the repository, and
the package workflow attests what it builds on every branch it runs on, so a
file built from unreviewed code would pass (ADR-0732). The GPG signature below
is the primary check; the attestation is a second one, not a replacement.
`release-workflow-tooling` requires a tagged recipe in the generated release
notes and tagged and rolling recipes in this guide. It checks the package
workflow and source ref in every published recipe.

Every tagged release and every rolling `latest` build carries an SBOM, as
`merovingian.spdx.json` (SPDX 2.3) and `merovingian.cdx.json` (CycloneDX 1.5),
each with a detached GPG signature. `scripts/generate_sbom.py` builds both from
`docs/dependencies/licenses.md` and the `subprojects/*.wrap` pins, inside the
workflow that publishes the release (ADR-0598). Vendored components carry
their pinned version and source SHA-256. Libraries a package links from its
build platform's OS packages carry no version, because one SBOM covers
packages whose platforms supply different versions. The generator refuses a
licence row or wrap it cannot map, so a new dependency cannot reach a release
without reaching its SBOM.

Repository changes are additionally covered by:

- [secret-scan.yml](../.github/workflows/secret-scan.yml) for Gitleaks-based
  history scanning
- [dependency-vulnerability-triage.yml](../.github/workflows/dependency-vulnerability-triage.yml)
  for PR dependency review and SBOM-backed vulnerability triage
- [pages.yml](../.github/workflows/pages.yml), which builds the documentation
  site with `mkdocs build --strict` on every branch and pull request and
  deploys it to <https://omg-software.github.io/Merovingian/> from `main`, so
  the published documentation always matches the latest merged release line

The only tarball a release publishes is the static Linux one
(`scripts/build-static-linux.sh`,
[ADR-0742](adr/0742-build-test-and-package-platform-lists-and-a-tag-ships-what-latest-ships.md)).
It holds:

- `bin/merovingian-server`
- `bin/merovingian-db-migrate`
- `libexec/merovingian/merovingian-fed-worker`
- `config/merovingian.conf.example`
- `docs/user-manual.md`, `docs/release-process.md` and
  `docs/security-review-checklist.md`
- `README.md` and `LICENSE`

It is built with the prefix `/usr`, so the server looks for the federation
worker at `/usr/libexec/merovingian/merovingian-fed-worker`. Install it there,
or set `federation.worker.binary` to where you put it. The tarball carries no
thumbnail worker.

## Starting a minor series: the upgrade fixture

Upgrades are supported from 1.0.0 onward, so this applies to minor series from 1.1 on.
A database written by the previous supported minor series must open, migrate and serve
under every candidate (ADR-0216). When the first version of such a series is cut (for
example 1.1.0), add the fixture of the last release of the series before it (there,
the last 1.0.x release):

```bash
python scripts/generate_upgrade_fixture.py <last-release-commit> tests/fixtures/upgrade/<last-release-version>
```

Then add scenarios to `tests/integration/test_database_upgrade_flow.cpp` that open that
fixture and serve it, and remove the previous fixture directory. Never regenerate a fixture from current code: it is
evidence only because the old release wrote it.

A pre-1.0 series start added no fixture and no upgrade test, and no pre-1.0 database is
supported. The migrations were collapsed into one initial schema in 0.12.47
([ADR-0224](adr/0224-pre-1-0-migrations-collapse-into-one-frozen-v1-schema.md)). A database
written by a build up to 0.12.46 is refused at startup: its schema ledger records migrations
this build no longer has (`schema_ledger_is_known` in `src/database/Migration.cpp`). A
database from 0.12.47 onwards records the same v1 step and passes that check, but v1 changed
seven times before it was frozen (0.12.59 to 0.12.86), and nothing compares a database's
tables with this build's, so such a database may lack columns and indexes this build uses.
The 0.12.47 collapse also removed the 0.11.13 upgrade fixture and its scenarios; there is no
fixture until the 1.1 series starts.

### The v1 schema is frozen from 1.0.0

Since 1.0.0, the v1 migration (the `initial_schema` step in `src/database/Migration.cpp`)
and `migrations/001_initial_schema.sql` never change. A schema change is a new numbered
migration (v2 onwards) that keeps deployed databases compatible. A unit test requires the
SQL file to match the build's v1 step statement for statement.

## Verifying release signatures

Every release tarball and package is accompanied by a detached GPG signature
(`.asc`). The signing key is an offline, long-lived maintainer key stored as a
secret of the GitHub Actions `release` environment, which only the `sign` job of
`sign-artifacts.yml` declares (ADR-0614). The environment admits only `main` and
`v*` tags; without it the signing job has no key and fails. `release.yml` also
refuses a tag whose commit is not an ancestor of `origin/main`. Operators can
verify artifacts without the GitHub CLI.

```sh
gpg --keyserver keys.openpgp.org --recv-keys 66DFCC50187C8E46B5ED85FD92A3A264F0A7BE20
```

Verify a release artifact:

```sh
gpg --verify merovingian_<version>_amd64-debian13.deb.asc \
  merovingian_<version>_amd64-debian13.deb
```

If the signature is valid, GPG reports a good signature from the maintainer
identity. A missing or invalid signature must be treated as a build or
distribution failure.

Release assets also include:

- `SHA256SUMS` over every asset, in both rolling `latest` and tagged releases,
  naming each file as published, so `sha256sum --check --ignore-missing
  SHA256SUMS` checks the assets downloaded beside it
- `merovingian.spdx.json` and `merovingian.cdx.json` SBOMs, in both
- `merovingian.licenses.json` machine-readable license summary, in both

Each of these has its own detached `.asc` signature.

## Operator sequence

The release operator should still run the normal local evidence path before
creating the tag:

```sh
sh scripts/setup-dev-env.sh --check-only
meson setup build -Dbuild_tests=true -Dbuild_fuzz=true
meson compile -C build
meson test -C build --print-errorlogs
sh scripts/reject-unsafe.sh
sh scripts/check-release-readiness.sh
```

Then run Complement against the candidate (see "Complement" below). It must be green
before the tag is created. The only exceptions are 1.0.0 and 1.0.1. The owner
waived the requirement for 1.0.0 because it was tagged without a green run and
the release-gate security audit was its gate instead
([ADR-0648](adr/0648-the-complement-blocker-is-waived-for-1-0-0-only.md)), and
for 1.0.1 because it fixes the vulnerabilities 1.0.0 ships
([ADR-0744](adr/0744-the-complement-blocker-is-also-waived-for-1-0-1.md)). The
waiver does not apply to 1.0.2 or any later release.

After that, create and push the release tag. It must be exactly `v` followed
by the version in `meson.build`, or the workflow refuses it:

```sh
git tag v<version>
git push origin v<version>
```

GitHub Actions publishes the release assets, SBOM included, for that tag.
The jobs in `release.yml` run only for a tag, so `tests/tooling` checks on
every pull request that each release build job installs a package for every
pkg-config module its build script checks. A tag is never moved once anything
has been published under it. The one moved tag is `v1.0.0`: its first run
failed before publishing, and the owner moved it to the fix commit without a
version bump ([ADR-0651](adr/0651-the-v1-0-0-tag-moves-to-the-release-workflow-fix-without-a-version-bump.md)).
The scheduled dependency-triage workflow keeps a separate vulnerability report
artifact.

## Complement

The 1.0.0 and 1.0.1 releases were tagged without a Complement run and carry no Complement
evidence ([ADR-0648](adr/0648-the-complement-blocker-is-waived-for-1-0-0-only.md),
[ADR-0744](adr/0744-the-complement-blocker-is-also-waived-for-1-0-1.md)). The 1.0.0 GitHub
release was deleted because it ships the vulnerabilities 1.0.1 fixes; its `v1.0.0` tag stays.
Every later release follows the steps below.

The external Complement suite runs against the candidate's Debian 13 (trixie) package
before the tag, and its signed result is attached to the release afterwards (ADR-0233,
ADR-0234, ADR-0235). Prerequisites are in `docs/dev-environment.md`, "Complement".

1. Take the candidate from the rolling `latest` prerelease built from the release
   commit: the `-debian13.deb` package and its signature, and the checksums and theirs:

   ```sh
   gh release download latest --repo OMG-Software/Merovingian --dir candidate \
     --pattern 'merovingian_*_amd64-debian13.deb*' --pattern SHA256SUMS --pattern SHA256SUMS.asc
   ```

2. Run Complement. The work directory must be empty, and the exit status is the verdict.
   Besides the signed checksums, the run checks the package's build provenance with
   `gh attestation verify`. `packages.yml` must have built exactly this file from one
   commit on `main`, and the run records that commit:

   ```sh
   python3 scripts/run_complement.py \
     --package candidate/merovingian_<version>_amd64-debian13.deb \
     --sha256sums candidate/SHA256SUMS --signature candidate/SHA256SUMS.asc \
     --work-dir ../complement-<version>
   ```

   A failure outside `tests/complement/skip-list.toml` is fixed, or listed with the
   evidence its category needs (`tests/complement/AGENTS.md`). A stale or missing
   entry is removed. Either way the run is repeated from an empty work directory.

3. Record the evidence. The exit status is 0 only for release evidence:

   ```sh
   python3 scripts/record_complement_evidence.py --work-dir ../complement-<version> \
     --package candidate/merovingian_<version>_amd64-debian13.deb --output-dir ../complement-evidence
   ```

4. Tag the commit the run recorded (`source.commit` in the results), and push the tag
   (above). Once the release workflow has published the release, sign and attach the
   evidence and the tested package. The publisher refuses a tag at any other commit. The
   release already has its own `-debian13.deb` build, and no asset is ever replaced, so
   the publisher attaches the tested bytes as `merovingian_<version>_amd64-debian.deb`
   (and `.asc`) ([ADR-0742](adr/0742-build-test-and-package-platform-lists-and-a-tag-ships-what-latest-ships.md)):

   ```sh
   python3 scripts/publish_complement_evidence.py \
     --results ../complement-evidence/complement-results-<version>.json \
     --log ../complement-evidence/complement-<version>.jsonl \
     --package candidate/merovingian_<version>_amd64-debian13.deb \
     --package-signature candidate/merovingian_<version>_amd64-debian13.deb.asc \
     --tag v<version>
   ```

The release notes' Complement section names the files. Readers verify each like any
other asset (`gpg --verify <file>.asc <file>`). The tested package's SHA-256 must equal
the `package.sha256` the results record, and its `/usr/bin/merovingian-server` the
`server_sha256`.

## Rolling latest packages

Pushes to `main` also trigger [packages.yml](../.github/workflows/packages.yml).
That workflow rebuilds packages for all supported platforms, replaces the
rolling `latest` GitHub prerelease, and uploads fresh package checksums:

| Artifact | Job |
|---|---|
| Ubuntu `.deb`, one each for 24.04 LTS, 26.04 LTS and 26.10, named `-ubuntu<release>.deb` | `deb` (reported as "Ubuntu <release> package"; `deb-all-releases` reports the required "Debian package") |
| Debian 13 (trixie) `.deb`, named `-debian13.deb` | `debian-pkg` |
| Fedora `.rpm`, one each for Fedora 44 and 45 (`.fc44`, `.fc45`) | `rpm` |
| RHEL-compatible `.rpm` (AlmaLinux 10, `.el10`) | `rhel-rpm` |
| OpenSUSE `.rpm`, one each for Tumbleweed (`.tumbleweed`) and Leap 16.0 (`.leap16`) | `opensuse-rpm` |
| FreeBSD 15 `.pkg`, named `-freebsd15.pkg` | `freebsd-pkg` |
| OpenBSD `.tgz`, named `-openbsd<release>.tgz` | `openbsd-pkg` |
| NetBSD `.tgz`, named `-netbsd<release>.tgz` | `netbsd-pkg` (a failure blocks publishing; re-run the failed job, [ADR-0502](adr/0502-every-bsd-job-is-required-and-the-netbsd-retry-cannot-rescue-it.md)) |
| Portable static Linux tarball (musl), named `-linux-static-x86_64.tar.gz` | `static-linux-fallback` |

Every package is x86_64, built with the hardened profile, and named after the platform it
installs on, renamed by the job that built it before it is attested. Debian 12 is not
packaged: Debian 13 is the minimum, and the static tarball covers older Linux
([ADR-0742](adr/0742-build-test-and-package-platform-lists-and-a-tag-ships-what-latest-ships.md)).

A tagged release ships exactly this set: `release.yml` calls `packages.yml`
(`distro-packages`) after the tag check, and `stage-package-assets` and
`sign-package-assets` run for a `v*` tag as for `main`, so the tag publishes the same
signed packages, SBOM, licence summary and `SHA256SUMS`
([ADR-0742](adr/0742-build-test-and-package-platform-lists-and-a-tag-ships-what-latest-ships.md)).
Its own `-debian13.deb` and the Complement-tested package, which the Complement step
attaches as `-debian.deb`, sit side by side. Publishing `latest` runs only for a push
to `main`, so a tag never touches `latest`.

Every packaging script configures Meson with `--buildtype=release`. Meson's
default `debug` build has no `_FORTIFY_SOURCE`, and the server refuses to start
when its startup hardening self-check cannot confirm it
([ADR-0148](adr/0148-packaging-paths-pass-buildtype-release-explicitly.md)).
A new packaging path must do the same, and be added to `PACKAGING_SCRIPTS` in
`tests/tooling/test_packages_workflow.py`.

Before attesting, the `deb` and `debian-pkg` jobs install the package they
built and run `scripts/check-startup-hardening-gate.sh` against the installed
`/usr/bin/merovingian-server`, as the `merovingian` user with an empty
capability bounding set. The job fails unless every startup hardening check
reports `enabled` and the server stops cleanly. The `docker-image` job does the
same for the `Dockerfile`: it builds the image and runs the gate inside it with
`--cap-drop=ALL --security-opt=no-new-privileges`. The `rpm` job does the same as
the Debian jobs, on each Fedora image. The `freebsd-pkg` job installs its package
with `pkg add` and runs the gate against `/usr/local/bin/merovingian-server` as
`nobody`. On any system other than Linux the gate sets
`federation.worker.apply_hardening=false`, because the worker's in-process sandbox
exists only on Linux. The image is not published;
the job is a gate on the recipe.

The `Dockerfile` pins `debian:trixie-slim` by the digest of its
multi-architecture index. To move to a newer base, read the current digest
(for example `docker buildx imagetools inspect debian:trixie-slim`, the
`Digest:` line of the index, not a per-platform manifest), replace it in both
`FROM` lines, and let the `docker-image` job prove the new image still passes
the gate.

Each package is individually attested with
`actions/attest-build-provenance` before upload. The signer is `packages.yml`
in both cases; the ref says which build it was. A package of a tagged release:

```sh
gh attestation verify <package-file> --repo OMG-Software/Merovingian \
  --signer-workflow OMG-Software/Merovingian/.github/workflows/packages.yml \
  --source-ref refs/tags/v<version>
```

A file of the rolling `latest` release, built from `main`:

```sh
gh attestation verify <file> --repo OMG-Software/Merovingian \
  --signer-workflow OMG-Software/Merovingian/.github/workflows/packages.yml \
  --source-ref refs/heads/main
```

Never drop `--signer-workflow` or `--source-ref` (ADR-0732, and "Tagged
releases" above).

The publish step also creates a detached GPG `.asc` signature for every
package (including `SHA256SUMS`) using the maintainer key. Verify with:

```sh
gpg --verify <package-file>.asc <package-file>
```

The publish step resolves and deletes the existing `latest` release with an
explicit `--repo "${{ github.repository }}"` scope before recreating it so the
artifact-only job does not depend on checkout state.

The static Linux fallback artifact is built on Alpine/musl with `-static-pie`
and packaged as `merovingian-<version>-linux-static-x86_64.tar.gz`. It is a
portability fallback for older Linux distributions that cannot easily consume
the `.deb` or `.rpm`; distro packages remain preferred where available because
their OpenSSL, libsodium, and libpq dependencies receive normal OS security
updates.
