# The release SBOM is generated from the licence inventory and wrap pins, inside each publishing workflow

* Status: accepted
* Date: 2026-11-10

## Context and Problem Statement

Releases and the rolling `latest` build must publish an SBOM. `sbom.yml` claimed to do this, but neither ever carried
one, for two reasons:

* Its attach step ran on the `release: published` event. Both publishing workflows create their releases with
  `GITHUB_TOKEN`, and GitHub starts no workflow from an event that token causes. On a push to `main` it only left a
  workflow artifact, never attached to `latest`.
* It ran Syft over the source tree. Syft has no Meson cataloger, so the SBOM it produced listed the 50 GitHub Actions the
  workflows use, and none of libsodium, OpenSSL, libpq, libcurl, SQLite, yyjson, libpng or libjpeg-turbo.

## Considered Options

* One SBOM per release, generated by `scripts/generate_sbom.py` from `docs/dependencies/licenses.md` and
  `subprojects/*.wrap`
* One SBOM per package, generated from each package's Meson build directory (`meson introspect`)
* Keep Syft over the source tree, and only change where it is published

## Decision Outcome

Chosen: one SBOM per release, as the owner decided on 2026-11-10, in SPDX 2.3 (`merovingian.spdx.json`) and CycloneDX 1.5
(`merovingian.cdx.json`) JSON. It is generated from two files the project already keeps accurate:

* `licenses.md` names every third-party component a shipped binary contains or links, with its SPDX licence;
* the wraps pin each vendored component to a source URL and SHA-256.

The vendored components (SQLite, yyjson, and the curl wrap the static Linux tarball links) carry their pinned version
and hash. The components each package links from its build platform's OS package carry no version. One SBOM covers
packages whose platforms supply different versions of them, and stating one would be false for the rest.

Both `release.yml` (`stage-release-assets`) and `packages.yml` (`stage-package-assets`) generate the SBOM into the
assets they stage before signing. It is therefore published with a detached GPG signature like every package, and is
listed in `latest`'s `SHA256SUMS`. `release.yml` now generates the licence summary at the same point, so it too is
signed. `sbom.yml` is removed. `check-release-readiness.sh` requires the generator, checks that both workflows call it,
and runs it.

The generator fails closed with exit status 2. It refuses:

* a row in a shipped licences table that it has no mapping for;
* a wrap that no component maps (other than the test-only `catch2.wrap`);
* a licences section it has not classified as shipped or unshipped;
* a wrap without a SHA-256 `source_hash`.

A dependency cannot reach a release without reaching its SBOM. Its output is deterministic: the creation time is
`SOURCE_DATE_EPOCH`, else the commit's committer time.

### Positive Consequences

* Every release and every `latest` build carries an SBOM that names the software it ships, signed by the maintainer key.
* Adding a dependency to `licenses.md` or `subprojects/` without classifying it for the SBOM fails the release-readiness
  gate in CI.

### Negative Consequences

* The SBOM cannot state which version of an OS-supplied library a given package was built against. The per-package
  option would, if that is later needed.
* `generate_sbom.py` holds a small mapping from licence rows to component names and wraps that must be kept with
  `licenses.md`. The fail-closed checks make a missed update loud, not silent.
* `dependency-vulnerability-triage.yml` still scans a Syft source-tree SBOM, which has the same blind spot. This
  decision does not change it.

## Pros and Cons of the Options

### One SBOM per package from `meson introspect`

* Good, because it records the exact resolved version and linkage of every dependency in each package.
* Bad, because it touches every package job (about 13, several in BSD VMs) and needs per-platform staging of the
  output. The owner chose the per-release SBOM.

### Keep Syft over the source tree

* Good, because it is already written.
* Bad, because the result does not describe the shipped software at all, so publishing it meets the requirement in
  name only.
