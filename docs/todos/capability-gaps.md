# Capability gaps

Open work per capability area. Status column reflects the current level in the
`not-started → planned → scaffolded → unit-covered → integrated → runtime-wired
→ spec-covered → production-gated` ladder.

**Reading this document.** A status here is a claim, not a proof — only rows backed
by a conformance test in `tests/conformance/` are independently verified. Two
failure modes have bitten us, so check for both when auditing:

1. **Silence is not coverage.** An unlisted endpoint may be unimplemented rather
   than complete. The Application Service and Push Gateway APIs were absent
   entirely while going unmentioned here until the 0.11.11 audit.
2. **Historical example (before 0.11.11):** `POST /pushers/set` returned 200 while discarding every pusher, and a push-rule row claimed coverage without behavior. Grep proves absence well; it does not prove behaviour.

When adding a capability, record what is *missing* as explicitly as what works.

A refusal is `403 M_FORBIDDEN` (`M_USER_SUSPENDED` for a suspended user), an event this room does not contain `404 M_NOT_FOUND`. `PUT /send` of an `m.room.redaction` goes through the same check and, before v11, has `content.redacts` moved to the top level. **Applying redactions** (`homeserver/redaction_service.cpp`, run for every event stored by the main process and once at startup): a redaction is applied once its target is stored, if the redaction sender's power level (taken from the power levels among the redaction's own `auth_events`) is at least the redact level or its domain is the target sender's domain (rooms/v3.md to v12.md "Handling redactions"). Applying overwrites the target's stored JSON with `events::redact_event`'s output, in the database and in memory, so the original content is deleted and no path can serve it; hashes and signatures stay, so the redacted form still verifies over federation. Until it is applied a redaction is withheld from clients (`database::redaction_is_withheld`, enforced in `sync::HistoryVisibility::can_see`, so `/event`, `/messages`, `/context`, `/sync`, sliding sync, `/relations`, `/threads` and `/search` all skip it) and raises no push; one that arrives before its target is held and applied when the target arrives; one that does not apply stays withheld. Clients are served the redacted event with `unsigned.redacted_because` (all read paths share `database::attach_redacted_because`) and redaction events with `redacts` in both places. A redaction of an `m.room.create` event is never applied (the server reads the room version from it). On the first start after the upgrade, redactions an earlier version accepted but never applied are applied. Conformance-covered in `tests/conformance/test_redaction_application_conformance.cpp` and `test_redaction_federation_conformance.cpp`. **Known gaps**: a redaction is judged once, with the power levels in its own `auth_events`, not re-judged if the room's state changes; a redaction of an event the server has not received waits indefinitely (there is no expiry). |

## RESOLVED (0.12.13, branch `fix/audit-critical-high-0.12.13`): membership-path receipt checks

**State: the implementation is complete, the failing test fixtures have been
rebuilt, and the full suite is green (`Ok: 54`, `Fail: 0`, `Timeout: 0`).
Nothing here was a production defect; the branch is ready to merge.**

ADR-0064 phase B2 brought the `/send` path onto the spec's receipt checks
("Checks performed on receipt of a PDU"). The final step extends the same
checks to the membership path (`runtime.federation.membership_acceptor` in
`src/homeserver/local_http_router.cpp`, serving `send_join` / `send_leave` /
`send_knock`):

* a content-hash mismatch REDACTS the event and processing continues, instead
  of rejecting it (spec step 3);
* the event is authorised against its own `auth_events` (reject), the state
  before it (reject), then current state (soft-fail) — steps 4, 5, 6;
* a rejected event is still stored, marked `rejected`, so later events that
  reference it can be authorised, but never updates state, never becomes a
  forward extremity, and the peer receives 403;
* a soft-failed event is stored, takes part in state resolution, and never
  flips the membership cache — this is what stops a join that references
  pre-ban history from re-admitting a banned user;
* rejections are logged with their reason (`Membership PDU rejected on
  receipt; ... reason=...`), which is the fastest way to diagnose the
  remaining failures.

Correction (0.12.36, conformance audit R06): the redaction above never ran for a
direct `send_join` / `send_leave` / `send_knock` or `/invite`, because the
request layer (`handle_send_membership`, `handle_invite`) still refused a hash
mismatch with 403 / 400 before the acceptor or invite handler saw the event.
Both now pass it on; the acceptor and the invite handler redact, and store,
authorise, sign and return the redacted copy. A signature failure is still
refused, now with 400 `M_INVALID_PARAM` as each endpoint's spec text asks.

### Why the suite was red

The new checks were strict in a way the old single current-state check was not.
Authorising against an event's own `auth_events` requires the SENDER to name
the events that permit it; authorising against the state before the event
requires real `prev_events`. Several fixtures predated those checks and built
join events with empty `prev_events` and/or empty `auth_events`. They passed
before because the room's current state happened to contain the join rules and
memberships. Rejecting them was correct: a conformant peer always names its auth
events (our own make_join template does).

**The checks were never relaxed to make the fixtures pass.** An earlier attempt
to relax the room-v12 `auth_events` rule was reverted for exactly this reason —
see `docs/adr/0062`..`0064` and the v12 conformance test citing rooms/v12.md rule
3.2. The fixtures were what was wrong.

### What was done

1. Rebuilt the failing fixtures to send realistic events using

### Also resolved: ADR-0064 phase C (backfill)

Phase C has shipped. `ingest_pdu_event` now attempts a bounded backfill from
an inbound PDU's origin when `prev_events` or `auth_events` are missing:
`POST /_matrix/federation/v1/get_missing_events/{roomId}` (up to 20 events),
then `GET /_matrix/federation/v1/event/{eventId}` for individual references,
capped at a configurable 16 general outbound calls per PDU by default (0.12.18), with a shared recovery call/deadline budget. Each returned event is verified
independently (content hash, signature, auth-events selection, auth against
its own `auth_events`) and stored as an outlier with a recorded after-state
group. If references remain missing after the capped attempt, the PDU still
returns `missing_prev_state` and is not applied. See `docs/event-engine.md`
"Phase C" and `docs/adr/0064-spec-conformant-pdu-ingestion-with-delta-state-groups.md`.

**Unresolved ordinary-PDU retention:** closed by R03 (ADR-0165). An ordinary PDU whose missing history/state cannot be recovered is retained in `deferred_pdus` (bounded, durable) and retried by `homeserver::retry_deferred_pdus`; one that cannot be retained is reported to the sender as a per-PDU error in the `/send` response. Still open: client visibility of the late event (it arrives in the timeline when it is placed, as any backfilled event does) and a retention cap that a hostile peer cannot fill for a room (the per-room limit of 100 can be consumed until those rows expire).

**Residual scope:** the membership-acceptor path
(`send_join`/`send_leave`/`send_knock`) does not yet backfill missing
references.
